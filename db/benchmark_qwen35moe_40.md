## Вывод

**Что работает идеально.** Персонал (сетевые показатели), база знаний, комментарии, управленческие решения — **10/10** на каждом. Модель точна: все 18 отвеченных вопросов проверены против БД — **ни одной фактической ошибки**. KB-инструмент работает безупречно: Q36/Q38/Q39 — 1 вызов, верный ответ, источник указан.

**Где модель валится — три отдельных причины:**

1. **«Потолок» зацикливания (главная)** — 15 из 22 провалов. На многошаговых вопросах (погрузка по классам, скорость, грузооборот) модель повторяет одинаковый SELECT 3–6 раз вместо того, чтобы сформулировать вывод. Q37 — рекорд: 19 вызовов. Это поведенческий предел, не проблема данных.

2. **Данных нет в схеме** — 6 провалов (D-группа: per-код, per-дорога, per-РЦКУ, Забайкальск отдельно). Модель корректно ищет, но indicator в metrics не существует — это **пробелы источника**, не ошибка модели.

3. **Сокращённые имена indicator** — Q3/Q5/Q7–Q10. Модель не угадывает «груз.», «в т.ч.» без триграммного `%`-поиска. Описание в `describe` предупреждает, но модель всё равно использует `ILIKE` по полному слову.

**Сравнение с 15-вопросным прогоном:**

| | 15Q | 40Q |
|---|---|---|
| Ответов | 8/15 (53%) | 18/40 (45%) |
| Sec/call | 1.63 с | 1.86 с |
| Точность на ответах | 8/8 (100%) | 18/18 (100%) |

Снижение % ответов объясняется тем, что 40Q включает больше «сложных» D-группы с отсутствующими данными. Точность на реальных ответах по-прежнему 100%.

**Рекомендации.** Приоритеты для улучшения:
- **Harness dup-query guard** — обнаружить повтор идентичного SQL и принудительно запросить вывод → поднимет на ~5–8 вопросов.
- **Предупреждение в `describe`** о неуникальности `indicator_number` → прямо устранит Q1/Q8/Q9.
- **Добавить данные** per-РЦКУ, per-дорога задержки (если источник предоставит) → разблокирует D-группу.
